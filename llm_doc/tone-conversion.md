# カラーを白黒（トーン化）

`効果 > 白黒-薄い/濃い/ラフ/シンプル` と `薄いカラー化` の処理を触るときに読む。
現行実装の何がまずかったか、作り直しで何を採ったか、何が未検証かを残す。

対象ファイル: `js/sidebar/effect/c2bw_tone.js`、`js/sidebar/effect/c2c.js`、
`js/ui/control/glfx-control.js`、`third/glfx/glfx.js`

数値はすべて実測。検証は現行シェーダを numpy で再現した検証台で行い
（この再現には途中まで ink の係数ずれがあった。第0章）、
処理コストはブラウザと同じ V8（Node v20.8.0）で測った。
検証に使った画像は AI 生成のアニメ調イラスト7枚（1024×1024 〜 1873×2480）。

### この作業で犯した判断の誤り（繰り返さない）

**指標が良くなった事を、結果が良くなった事と取り違えた。**
使っていた3指標（線の破断率 / 階調誤差 / 偽の輪郭）は、
ユーザーが実際に問題にした4点を**どれも測れていない**。

| ユーザーの指摘 | 指標で検出できたか |
|---|---|
| 髪の毛の線先が黒く塗られている | ✗ |
| トーンが荒い | ✗ |
| トーン対象がずれている | ✗ |
| 後ろ髪付近が黒く潰れている | ✗ |

指標は「前より悪くなっていないか」の見張りにしかならない。
**採否は必ず等倍の実画像を見て決める。** 部位ごとに切り出して原画と並べる事
（`poc/tone/lead_render.py` の `crop_box` / `save_gray`）。
サムネイルに縮小すると網点が消えて別物になるので、縮小して判断しない。

**符号の向きを、算術で確かめずに「最有力の原因」と書いた。**
旧 7-1 は「黒点を `g` から測っているせいで面の暗い側が黒に張り付く」と書いていたが、
カーブは `t = clip((g − black)/(white − black))`（t=1 が白）なので**黒点を上げれば暗くなる**。
旧 7-1 の修正案（`face` から測る＝黒点 0.3464→0.5045）は、非難した現象を自分で起こす。
実画像を切り出す前に、式に数字を入れれば潰せた誤りだった。
**符号の向きは、実画像を見る前に式で確かめる。**

**指標が症状を測れているかを確かめないまま使った。**
s8 の最大の失点だった光沢クサビの消失を、指標は1つも捉えていなかった（第10章）。
**指標は、既に出ている目視の答えを再現できるかで検定する。再現できない指標は捨てる。**

**比較の基準そのものを検証していなかった。**
「現行の再現」を名乗る `harness.glfx_ink` が現行アプリを再現できていなかった。
`glfx.js` は `strength = b**5` を渡すのに検証台は5乗しておらず、**ink が256倍強い**状態だった
（薄い/濃い 0.25→0.25⁵ で256倍、ラフ 0.42→0.42⁵ で32.1倍。シンプルは ink 段を通らないので無影響）。
修正後の `s1_current`（`src_full`）は s1 平均 0.9488→**0.9714** / 黒画素率 4.74%→**2.67%**、
s2 平均 0.9388→**0.9652** / 6.09%→**3.43%**。
**旧値で読んではいけないのは2箇所**（`FINDINGS.md` 追補B-1 の表の s1/s2 と J-5 の s1現行列）。
黒点・白点・`tone_r`・ゲート・ピッチの結論は ink を使わないので変わらない。
**「現行の再現」を名乗るコードは、参照実装と係数まで突き合わせる。**

**比較の立て方が非対称だった。**
長らく `s8_final`（作り直し案の途中段）を「現行」として並べており、
**現行アプリ（`s1_current`）と比べていなかった。**
さらに現行側だけが「薄い」1プリセット、新案側はプリセット無しという非対称な比較で、
ユーザーの「オリジナル処理との差が分からん」という指摘で判明した。
**比較は、現行アプリそのものと、同じ土俵（同じプリセット）で並べる。**

**掃引範囲が判断したい方向の片側しか含んでいなかった。**

## 1. 現行実装の何がまずかったか

工程は `ink` → `brightnessContrast` → `dotScreen` の順で、全画素に同じフィルタを掛けている。
報告された不具合は「線が細かく分かれる」「髪のツヤの周りに枠ができる」の2件で、
**原因は3つあり、互いに独立している**。

### 1-1. 線が分断される ── 黒が浮いた状態で網点を掛けている

`brightnessContrast` は明るさを足してから前後に伸ばすので、純黒が浮く。

```glsl
color.rgb += brightness;
color.rgb = (color.rgb - 0.5) / (1.0 - contrast) + 0.5;
```

`dotScreen` は `average*10.0 - 5.0 + pattern()` で、`pattern()` の振れ幅は ±4。
黒が浮いていると、この加算で黒線の内部が白に振れる。

| プリセット | BC後の純黒 | dotScreen後の最大値 | 網点で表せる入力の範囲 |
|---|---:|---:|---|
| 薄い | 0.269 | **+1.69** | −0.110 〜 0.410 |
| 濃い | 0.141 | **+0.41** | −0.032 〜 0.592 |
| ラフ | 0.347 | **+2.47** | −0.146 〜 0.326 |
| シンプル | 0.088 | −0.12 | 0.010 〜 0.690 |

正の値が出るプリセットで黒線に白点が開く。シンプルだけ黒が保たれるのはこのため。

**併せて、薄いは入力 0.410 より明るい所がすべて純白に飛ぶ。**
髪（輝度 0.6〜0.75）は内側も外側も白になり、階調が残らない。

### 1-2. 枠が出る（その1）── `ink` の利得が10万倍

```glsl
edge = max(0, (5x5の平均) - (3x3十字の平均));
out  = color - dot(edge,edge) * strength * 100000.0;
```

完全に黒くなる中心-周囲差を逆算すると:

| strength | 完全に黒くなる1チャンネルの差 |
|---|---|
| 0.25（薄い） | 0.0037 = **0.93 / 255階調** |
| 0.42（ラフ） | 0.0028 = **0.72 / 255階調** |

**5x5 の範囲で明るさが 8bit で1階調ずれるだけで真っ黒な線が引かれる。**
実画像の本物の線の応答は 0.22〜0.41（p50〜p90）なので、
閾値が本来必要な値の **60〜100倍下**にある。
髪のツヤの縁のような「なだらかな明暗の変化」がすべて線になる。

副作用として、JPEG q70 を1回通すだけで線画素が **+65.7%** 増える。

### 1-3. 枠が出る（その2）── 網点の濃度応答が非線形

`dotScreen` のしきい値を素直に振ると、面積の応答がS字に曲がる。
**中間調の傾きが 2.15**（入力の変化に対して濃度が2倍速く動く）。
ゆるい勾配がここを通ると濃度が急に変わり、それも段差＝枠に見える。
`average*10-5` の10倍ゲインはこれに重なっている。

ゆるい勾配（0.30→0.70 を1000pxかけた）の理想からのずれ（×1000）:

| | ずれ |
|---|---:|
| 線形化なし | **49.40** |
| 現行式の場 `cos*cos` | 46.95 |
| 逆関数で線形化 | **2.34** |

### 1-4. 透過画像の扱い（未修正の癖）

- `ink` は近傍5x5の **RGB のみ**を見てアルファを見ていない。透明領域の RGB（多くは0）を
  巻き込むため、不透明領域の縁に黒いエッジが出る
- `dotScreen` は透明画素の average=0 を `average*10-5` に通すので、透明領域の RGB が黒に潰れる。
  α=0 なので直接は見えないが、後段でスケール補間が掛かると縁に黒が滲む

### 1-5. 現行4プリセットが実際にやっている事（`src_full.png` の実測）

作り直しの比較相手はこれ。**思っていたものと違う。**

- **変えているのは実質2軸だけ。** `brightness` と `contrast` は4プリセットとも常に同値で、
  合わせて1つの「濃さ」つまみ。もう1軸が `inkStrength`。
  `dotSize` は4つとも 1.5 で不変、`dotAngle` は振っても全体黒画素率が 1.07倍でほぼ効かない。
  分離実験では b=c が黒画素率 2.00倍、ink が 3.02倍（線残存 19.96→63.50）で、
  **ink の方が効きが大きい**
- **名前と濃さの順が一致していない。** 網点が乗り始める原画輝度は
  ラフ 0.385 < 薄い 0.475 < 濃い 0.670 < シンプル 0.775 で、
  **「ラフ」が最も薄く「シンプル」が最も濃い**
- **ベタ黒になる閾値は4つとも負**（シンプルのみ 0.010）。
  **面からベタ黒は出ず、現行の黒はすべて `ink` 由来**
- **実質「髪にだけ網点が乗る」設定。** 肌・服・背景の黒画素率は 0.00〜0.37% しかなく、
  濃さの差は髪の 14.04〜22.01（1.57倍）に集約されている
- ラフとシンプルは全体黒画素率が同じ 3.46% だが内訳が逆。
  **シンプルは面（髪 22.01）、ラフは線（線残存 65.93）で稼ぐ**

## 2. 作り直しの構成

工程を3段に割り、**線と面を分けて、面にだけ点を打つ**。

```
輝度(BT.601)
 → closing(g, k)                 線を消した「面だけ」の明るさ。max→min の2段
 → line  = smoothstep(closing - g)            モルフォロジー black-hat
 → wline = smoothstep(g - opening)            white-hat（ベタ黒の中の白い線）
 → tone  = ソフト量子化(トーンカーブ(box(closing, tone_r)))
 → dots  = 整数格子の網点(tone)
 → out   = dots * (1 - line) を wline で白く抜く
```

### 2-1. 線の検出は black-hat（`closing(g) − g`）

**単調な段差に対して数学的に 0 を返す**のが決め手。合成テストで、
振幅 0.10 / 0.15 / 0.25 / 0.40 × AA幅 1〜8px のすべての組み合わせで **0.0000** を確認した。
一方、線（谷）に対しては幅が `2r-1` 以下なら太さに依らず深さそのものを返す。

| 入力 | black-hat r=4 の応答 |
|---|---:|
| 単調な段差 振幅0.10〜0.40、AA幅1〜8px（全組み合わせ） | **0.0000** |
| 線 深さ0.11、幅1〜7px | 0.1100 |
| 線 深さ0.53、幅1〜7px | 0.5300 |

`ink`（中心-周囲差）は同じ段差に 0.047 を返し、薄い線の 0.076 との分離比が 1.6 しかない。

**採ってはいけない代替:**

- **`ink` に閾値を入れて補正する** … 枠は消えるが**太い線が中抜きの輪郭になる**（まつ毛が輪郭線化する）
- **箱平均の差（`box(g,r) - g`）** … 段差の振幅の半分が残るので暗さゲートが必要になり、
  そのゲートが薄い毛筋を殺す。7枚で薄線の残りが **負（明暗が反転）** になった
- **Sobel / DoG** … 線が破線になる
- **ridge（4方向の両側テスト）** … 精度は同等だが numpy で 349ms 対 black-hat 43ms

**注意: `line_blackhat` という名前の実装が検証台に2種類ある。**
`pre_stage.line_blackhat` は箱平均の差の近似で、上の性質を持たない。
モルフォロジー版（`stage_post.line_blackhat`）が正しい方。

**現行の検証台は暗さゲートを落としている（バグ）。**
`pre_stage.pre_B` / `pre_G` が持っていた `line_darkness(g, d0, d1)` の掛け算が
`lead_stages` に無く、black-hat の応答だけで黒を置いている。
そのため `line>0.5` の画素の **33.8% が原画 `g>0.45`、13.1% が `g>0.60`** で、
`face` が 0.85 以上（ほぼ紙白）の画素でも 0.903% が純黒になる。
**ただしゲートを戻すのは誤りだった。** 絶対輝度で線の明暗を切ると、
残したい服の線が止めたい髪の上の線を輝度で完全に内包しているため分離できない。
**ゲートは付けない**のが採用案（第9章 9-1）。

### 2-2. 網点は整数格子（スーパーセル法）

格子を整数ベクトル `(a,b)` と `(-b,a)` で張ると画素格子と厳密に整合し、
**`(a²+b²)/gcd(a,b)` 画素ごとに完全に繰り返す**。
そのため「タイル位置 × tone」の2次元表を1枚作って引くだけで済む。

| 実装 | 1.78Mpx | 4.65Mpx |
|---|---:|---:|
| **タイル位置×toneの2次元表（AA+ss2 込み）** | **3.2 ms** | **11.2 ms** |
| 画素ごとに三角関数（ss=2、16回/px） | 662 ms | 1700 ms |
| 誤差拡散 Floyd-Steinberg（逐次） | 15.0 ms | 43.2 ms |

**`T×T` の閾値行列＋ハード比較にしてはいけない。** 出力が2値なので中間濃度が
タイル内の画素数でしか表現できず、階調が `T²` 段に量子化される。
(3,3) で濃度誤差 **0.2758**（2次元表なら 0.0052）。細かいピッチほど悪化する。

**ピッチは画像サイズに追従させる。** 固定にすると 2480px と 1024px で
絵に対する点の細かさが約 2.4倍ずれる。

```
希望ピッチ = clamp(長辺 / 344, 3.0, 9.0)  → 下の梯子から最も近い段
```

| (a,b) | ピッチ | 角度 | 最小タイル | 表サイズ | 作成 |
|---|---:|---:|---|---:|---:|
| (3,2) | 3.606 | 33.7° | 13×13 | 42KB | 1.03 ms |
| (4,2) | 4.472 | 26.6° | 10×10 | 25KB | 0.45 ms |
| (5,3) | 5.831 | 31.0° | 34×34 | 289KB | 5.88 ms |
| (6,3) | 6.708 | 26.6° | 15×15 | 56KB | 1.52 ms |
| (6,4) | 7.211 | 33.7° | 26×26 | 169KB | 3.62 ms |
| (8,4) | 8.944 | 26.6° | 20×20 | 100KB | 2.09 ms |

角度を 26.6〜33.7度に絞ってあるのは、自由に選ばせると画像ごとに
14度→26度→33度と飛んでトーンの性格が変わるため。梯子は6段しかないので
`Map<"a,b,ss,aa", table>` に持てば作り直しは事実上ゼロ（全段で合計 14.6ms・681KB）。

**この梯子から採ったのは (4,2) 4.472px / 26.6度（8-1）。**
一度 (3,3) 45度に変えたが、下の縮小耐性のとおり `(a,a)` が唸るので撤回した。

**角度について:** 「45度がモアレに強い」は測定では支持されなかった。
モアレを決めていたのは角度よりピッチ。角度で明確に差が出たのは**縮小耐性**で、
このアプリはレイヤーを拡大縮小して配置するのでこちらが効く。

| 格子 | 縮小時の最悪ムラ（×1000、倍率0.5〜0.9） |
|---|---:|
| (3,0) 0° | 19.09 |
| (3,3) 45° | 8.72 |
| (4,4) 45° | 1.43 |
| **(4,2) 26.6°** | **0.01** |

`(a,a)` や `(a,0)` は2つの空間周波数が同じ大きさで揃うため特定の倍率で強く唸る。
**0度（画素格子と平行）だけは見た目でも明確に劣る**（網戸に見える）。

**この表の数値は再現できない**（実装が残っておらず定義を復元できない。(4,4) の順位が食い違う。8-1）。
**`(a,a)` が唸るという結論だけは、取り直した測り方でも成り立つ。**

### 2-3. 濃度の線形化と、白地の濁りの補正

しきい値は「場の分布の (1-cov) 分位点」を奇数次多項式で当てる。

```
x = 1 - 2*cov
thr = x*(0.507524 + x²*(1.061313 + x²*(-1.026793 + x²*0.464224)))    max誤差 0.0070
```

3次までだと 0.0241、9次にしても 0.0051 なので7次で打ち止め。
厳密な分位点（LUT）に差し替えても残差は改善しない（残るのは網点自体の離散化で、
8bitの1階調 = 3.9/1000 未満）。

**アンチエイリアス由来の白地の濁りを別途補正する。** インク率0でも AA の帯が
場の最大値に掛かるため、タイルの2割の画素が 248/255 になり白地が薄く濁る。
しきい値が場の最大値を AA の半幅ぶん超える倍率（guard）を場から実測して掛ける。
**AA幅は場の局所勾配に比例して画素ごとに違うので、一様に広げる補正では足りない。**
guard はハードコードせず、格子と ss と aa から毎回計算する。

### 2-4. 白点は画像から決まる。黒点は決められなかった

- **白点 = 明部の輝度ヒストグラムの最頻値 − margin×幅**。探索は `黒点 + 0.5×幅` より明るい側に限る。
  margin の採用値は **0.15**（0.11 では肌に乗り、0.18 では全体が薄くなる。第9章 9-1）
- **黒点 = 輝度の下位2% は破綻している。** 5枚での比較では**固定 0.10** が最も予測可能で、
  7枚の目視でも代償は出なかった（第9章 9-2）

白点を「幅の割合」で決める版は破綻する。小さな鏡面ハイライトが上位2%を押し上げると
白点も一緒に上がり、**面積の広い薄灰色の地が紙白に落ちない**（地の出力 0.861）。
最頻値方式にすると 0.999 になり、他5枚は変化なし。

探索範囲の制限は必須。付けないと、ベタ黒が過半を占める絵（53%が輝度<0.08）で
最頻値が黒側に落ちて**白点が負**になり、中央値が1.0の絵では探索区間が空になる。

**黒点が破綻する理由。** `src_full.png` で真のインク（`g<0.15`）は画像の **0.49%** しかなく、
線（`line>0.5`）も 2.95% でその `g` の中央値は 0.353。
下位2% = 0.3464 は既にインク層を抜けて、絵の暗い中間調に着地している（第7章 7-1）。
「8枚で手で選んだ値と一致した」は、ベタ黒が広く写った絵に偏っていたための一致だった。

黒点の規則を5枚（`src_full` / `t1_darkbg` / `t4_texture` / `t5_solidblack` / `t6_scene`）で振った結果。
偽ベタ黒 = 原画 ink<0.75 なのに出力 ink>0.92 の画素の割合、
ベタ黒保持 = 原画のベタ黒面が出力でもベタのまま残る割合:

| 規則 | src_full の黒点 | 偽ベタ黒（5枚の最悪） | ベタ黒保持 t6 |
|---|---:|---:|---:|
| 現行 下位2% | 0.3464 | 1.015% | **67.3%** |
| **固定 0.10** | 0.10 | **0.000%** | 36.5% |
| 下位0.5% | 0.1513 | 0.000% | 36.5% |
| 線を除いた下位2% | 0.4126 | **3.826%** | 78.4% |
| 暗部の谷 | 0.0039 | 0.000% | 16.7% |
| 線率90%の上限 | 0.2200 | 0.002% | 15.2% |

**この「ベタ黒保持 t6」は当てにならない。** `t6` のベタ黒画素は全体の 0.2% しかなく、
この5枚のうち真黒が十分あるのは `t4` だけ（`src_full` / `t1` / `t5` は真黒 0%。9-2）。
偽ベタ黒の列は母数が違うので影響を受けない。

- **線マスクを除外して測る案は逆方向で最悪。** 暗い母集団が消えるぶん黒点が上がり
  （src 0.3464→0.4126、t1 0.1614→0.2638）、偽ベタ黒が増える。`face` ベース案と同じ誤り
- **暗部の谷 / 線率の上限は破綻する。** 谷は5枚中3枚が最暗ビン（0.0039）へ縮退し、
  線率の上限は3枚で条件を満たす閾値が存在せず 0.0000 に落ちる
- **パーセンタイルは動くが安定しない**（下位0.5% で 0.0000〜0.1853 の幅）
- **固定値でベタ黒が白飛びする事は無い。** ベタ黒が53%を占める t4 の保持率は
  0.08→98.3% / 0.10→98.5% / 0.12→98.6% で、**現行の下位2%（97.8%）より高い**。
  t4 のベタ黒は `g=0` 付近にあり黒点の位置に鈍感。合格は固定値だけで、次点は 0.12
- **黒点を下げる代償は「本物のベタ黒が保てない」事。** 破綻するのは
  **ベタ黒が `g` 0.10〜0.15 付近にある小面積の絵**。劣化の半分は `tone_r=8` 由来で、
  `tone_r=2` にすると t6 の保持が 36.5%→48.8% に戻る。残りは線チャンネルに
  ベタ床 0.20 を足して 52.6%（0.25 まで上げると偽ベタ黒が戻り始める）
- **t6 の保持率が下位2%でも 67.3% しかないのは指標側の事情。**
  t6 のベタ黒面は全体の 0.20% しかなく、17px窓の平均が周囲を巻き込んで薄まる。
  現行の欠陥ではないので、この数字を根拠に何かを直そうとしない
- 紙白のインク率はどの規則でもほぼ変化しない（src 0.0017〜0.0018）

白点側の穴は残る。**肌のような広い明るい面を紙と区別できず、腕全面に網点が乗る**（第7章 7-5）。

### 2-5. 合成は `min` ではなくアルファ合成

```
out = dots * (1 - line)
```

`min` だと α=0.3 の薄い線が網点に負けて出ない。アルファ合成なら
アンチエイリアスの灰色がそのまま灰色で残り、ジャギも保たれる。

**ベタ黒の中の白い線は別に守る。** 黒線は網点から守っていたが白線は守っておらず、
服のシワなどが点線に割れていた。white-hat（`g − opening(g)`）で拾って白く抜く。

| 画像 | 保護なしで白線が消えた率 | 保護あり |
|---|---:|---:|
| 白シャツ＋黒スカート | 0.541 | **0.117** |
| 1873×2480 | 0.825 | **0.352** |
| やわらかい陰影 | 0.742 | **0.245** |
| 薄灰色の地 | 0.878 | **0.520** |

**白線側の閾値は黒線側と連動させない。** 黒 0.055 に対し白は 0.10 が必要で、
連動して下げるとベタ黒の内部を 3.1% 白く抜く。この非対称は経験的で理屈は未検証。

## 3. 面の量子化 ── 「枠」と「まばら」の綱引き（前提が実測で崩れた）

実際のスクリーントーンは濃度が数段に分かれているので、量子化した方が漫画らしく見える。
**ただし量子化は今回消したい境目を作る方向に働く** ── と考えて既定を中間に置いていたが、
**`post_w=0.25` は帯化としてほぼ効いていない。**
後ろ髪の相異なる濃度値は posterize あり 1001個 / なし 999個で、実質は上下端のクランプだけである。
綱引きとして調整していたつもりの箇所が、別の働きしかしていなかった。

| | ツヤの見え方 | 面の見え方 |
|---|---|---|
| 硬い量子化（post_w=0） | **硬い縁を持った白い穴**になる | 最も均一 |
| 連続階調（post_w=0.5） | 点が徐々に小さくなり**境目が消える** | 髪一本ごとの明暗を拾い**まばら**になる |

数値でも連続がわずかに上（階調誤差 0.0633 → 0.0601、線の破断率 0.0216 → 0.0196、
false_edge も全プリセットで連続の方が小さい）。

上下端のクランプは、綱引きとは別の効き方をする。

- **`post_w=0.25` は中間グレーの原因ではない。** post_w=0 で中間グレーは 6.58%→6.74%、
  posterize を外すと 6.86% と**増える**
- **下端クランプは黒潰れに寄与する。** `t ≤ 0.0625` が完全な 0 に落ち、
  現行黒点では `face ≤ 0.3794` が該当する（第7章 7-4）

**「まばら」は面のぼかし（`tone_r`）で抑える。**
髪一本ごとの明暗は消え、大きな陰影は残る。線は別チャンネルなので均しても細らない。
**ただし既定に置いていた `tone_r=8`（17px窓）は上げすぎだった。**
面の濃度が輪郭を越えて滲み、髪から8px以内の紙白が髪の暗さを浴びる（第7章 7-2）。
実測では `tone_r=2` の方が肌の被覆・ベタ黒保持・全体誤差のどれでも良い。

**段数を3まで減らしてはいけない。** 髪と髪の影が同じ段に潰れ、
境目の出方も全条件中で最悪（false_edge 0.0232、4段なら 0.0083）になる。
段を硬くするなら段数は減らせない。

## 4. やってはいけない事

- **線検出の前にノイズ除去を入れない。** 実測で線の破断率が
  box3 で 0.19、median3 で 0.126、bilateral5 で 0.028（無しは 0.0107）。どれも線を劣化させる
- **彩度を考慮した輝度を使わない。** 赤と青が共に 0 に潰れ、白に近い地が白点を割る
- **線検出の半径を画像サイズに追従させない。** 線の太さは画素で決まる。
  画像幅が 944→1873 と2倍でも「幅3px以下の割合」は 50〜56% で動かない
- **画像によって処理経路を変える分岐を入れない。** 「暗い面が4%以上のときだけ white-hat を掛ける」
  等の条件分岐は 59ms 節約できるが、同じプリセットなのに結果の性格が変わり、原因の切り分けができなくなる

## 5. 実装先と処理コスト

### 5-1. 2D canvas（CPU）で新規モジュールを作る

**glfx には自作フィルタを登録する口が無い。** 外へ出ているのは `fx.canvas` と
`fx.splineInterpolate` の2つだけで、シェーダクラスも `simpleShader` 相当も
クロージャ内に閉じている。生えているフィルタは26個で固定。

`fxCanvas._.gl` に相乗りする事は理屈上できるが、圧縮済みライブラリの内部表現
（`_.texture` / `_.spareTexture` / `drawRect` の buffer 名）に依存するので採らない。

**前例がある。** `HtmlCanvasUtil.enhanceDarkRegionsCPU`（`js/core/util/html-canvas-util.js:56`）が
同じ形の CPU 1パス処理で、`効果 > 黒強調` として一括適用にも乗っている。繋ぎ込みも同じ型を使う。

```
ImageUtil.fabricImage2ImageData → 純関数 → putImageData → ImageUtil.replaceImageByDataURL
```

### 5-2. `c2c.js`（薄いカラー化）を壊さない条件

`c2c.js:16` で差し替え前の要素を掴んで `:30` で重ねている。
**元の要素に in-place で書き戻すと `c2c` が黙って壊れる**（「重ねても色が乗らない」形で出る）。
`fabricImage2ImageData` は別の temp canvas を経由するのでこの前提を満たす。
他に、画素数を変えない事・デコード完了後に resolve する事・
`object` の top/left/scale/width/height を保つ事（`replaceImageElement` が担当）。

### 5-3. 処理コスト（Node v20.8.0、1160×1536 = 1.78Mpx）

| 処理 | 1.78Mpx | 4.65Mpx |
|---|---:|---:|
| 輝度化 1パス | 3.3 ms | 10.9 ms |
| トーンカーブ 1パス | 2.9 ms | 5.3 ms |
| 分離ボックスぼかし r=2 | 11.2 ms | 39.6 ms |
| 5x5 を直接舐める（現行 `ink` と同形） | 46.6 ms | 111.5 ms |
| closing（max+min の横縦4パス） | 46.5〜58.1 ms | |
| 網点（表引き） | 3.2 ms | 11.2 ms |
| 線の抽出＋合成 | 17.1 ms | |
| RGBA 書き戻し | 2.5 ms | 9.7 ms |

通しで 1.78Mpx が 160ms 前後、4.65Mpx が 300ms 前後の見込み。**JS 実装は未着手。**

**網点はピッチを変えてもコストが変わらない**（画素ごと1パスの表引き）。効くのは `ss` だけで、
`ss=2` は 1.78Mpx を 7.13Mpx 分に増やす（4倍）。

**max/min フィルタの実装で踏む罠:**

| 半径 | 単調デック | 直接展開 | vHGW（パディング整列版） |
|---|---:|---:|---:|
| r=2 | 76.6 ms | **12.5 ms** | 13.9 ms |
| r=3 | 80.5 ms | 16.1 ms | **15.0 ms** |
| r=4 | 82.5 ms | 19.5 ms | **14.4 ms** |
| r=6 | – | 26.0 ms | **15.9 ms** |

- **単調デックは半径が小さいと逆に遅い**（r=2 で6倍）。r≤2 なら直接展開、r≥3 なら vHGW
- **縦方向は「行ごとに前の結果と比較して累積」が最速。転置は不要**（stride 直接より速い）
- **vHGW は端を r だけパディングして窓 `k=2r+1` のブロック境界に整列させないと、
  外周 `r+1` 画素で誤った値を返す。** 素朴に書いた版は素朴実装との最大差 0.56。
  パディング後の長さを k の倍数に切り上げ、余りを `-Infinity` で埋める
- **`pick = isMax ? Math.max : Math.min` で切り替えると呼び出し位置が多相化し、
  min だけ 278ms（max は 52ms）になる。** max と min は別関数として書き分ける
- **`Math.pow` は単体で 31ms。** 入力が8bitなので256段の表引きに置換できる（近似ではなく厳密一致）
- **closing は前処理（面）と線検出で共有する。** 1回だけ計算すれば足りる

### 5-4. 一括適用は無改修で通る

`c2bwApplyToImage(object, preset)` のシグネチャと
「履歴コミットと進捗表示は呼び出し側が持つ」規約（`c2bw_tone.js:51-52`）を守れば、
`effect-batch.js` も `c2c.js` も触らない。
`setElement` は自動コミット網に検知されないので、明示コミットを崩さない事
（`llm_doc/review-checklist.md` 項番21）。

## 7. 原因の特定結果

等倍の実画像と `poc/tone/diag_*.py` の実測で切り分けた。調査全文は `poc/tone/FINDINGS.md`。
対象は `poc/tone/lead_stages.py` の `s8_final(src_full.png)`（1160×1536）、
補助に `t1_darkbg` / `t4_texture` / `t5_solidblack` / `t6_scene`。

| ユーザーの指摘 | 主因（寄与順） |
|---|---|
| 後ろ髪付近が黒く潰れている | 7-1 黒点 / 7-4 posterize の下端クランプ |
| 毛先が黒く塗られている | 7-1（黒画素の66〜70%）/ 7-3 線の暗さゲート欠落（30〜34%） |
| トーンが荒い | 7-1。髪が被覆率60〜95%に置かれ点が繋がる。網点エンジン自体は正常 |
| トーンが乗るべきでない所に乗る | 7-2 `tone_r=8` の暗さ漏れ / 7-5 白点 |

### 7-1. 黒点 0.3464 が絵の暗い中間調に着地している（最大）

`g` の下位2% = 0.3464。しかし真のインク（`g<0.15`）は画像の **0.49%** しかなく、
線（`line>0.5`）は 2.95% でその `g` の中央値は 0.353。**黒点は既にインク層を抜けている。**

| 閾値 | 未満の画素 | うち line>0.5 |
|---|---:|---:|
| g < 0.15 | **0.49%** | 94.4% |
| g < 0.25 | 1.20% | 87.3% |
| g < 0.3464 | 1.99% | **72.6%** |
| g < 0.45 | 3.99% | 48.8% |

茶髪の陰（`face` 0.35〜0.40）が `t ≈ 0.01〜0.10` ＝被覆率 90〜99% になり、網点が繋がってベタになる。
黒点掃引（後ろ髪、白点 0.8742 固定。後ろ髪の原画インク率は 0.3062）:

| black | 0.05 | 0.10 | 0.15 | 0.25 | **0.3464** |
|---|---:|---:|---:|---:|---:|
| 偽ベタ黒% | 0.00 | 0.00 | 0.00 | 0.00 | **8.77** |
| インク絶対誤差 | 0.0646 | **0.0641** | 0.0670 | 0.0792 | 0.1259 |

**後ろ髪の偽ベタ黒を単独で 8.77%→0.00% に決める唯一の要因**で、0.25 以下ならどの値でも 0.00%。
黒点の規則そのものの比較は第2章 2-4。

### 7-2. `tone_r=8`（17px窓）が面の暗さを空間的に漏らす

`face = box(closing(g), 8)` は17px窓なので、髪から8px以内というだけで紙白が暗くなる。
原画 `g=0.8822`（ほぼ紙白）の首すじが `face 0.7901` まで下がり、被覆率 0.0029→**0.1665**。

肌のうち網点が乗る割合（髪からの距離別）:

| tone_r | 1-4px | 4-8px | 8-12px | 20-60px | 肌全体 |
|---|---:|---:|---:|---:|---:|
| 8（現行） | 98.5% | 70.7% | 32.3% | 6.7% | 7.3% |
| **2** | 42.7% | 13.0% | 11.4% | 4.9% | **3.7%** |

肌に網点が乗る件では**白点より効くレバー**。ベタ黒保持の回復にも効く（2-4）。

### 7-3. `POST.line_blackhat` に暗さゲートが無い（バグ）

`pre_stage.pre_B` / `pre_G` が持っていた `line_darkness(g, d0, d1)` の掛け算を
`lead_stages` が落としている（2-1）。線は明るさと無関係に黒を置く。

| face 帯 | line>0.5 の画素（全体比） | 最終出力の中央値 |
|---|---:|---:|
| 0.30-0.50 | 0.086% | 0.000 |
| 0.50-0.70 | 0.943% | 0.000 |
| 0.70-0.85 | 1.015% | 0.000 |
| **0.85-1.01** | **0.903%** | **0.000** |

毛先の黒画素の **30〜34%** がこの経路のみに由来する（後ろ髪では 19.0%）。
暗さゲート `(0.36, 0.54)` を掛けると `line>0.5` は全体 2.95%→1.94%、後ろ髪 8.48%→6.18%。
**ただしこのゲートは採らない。** 白い服の線を巻き添えにする（第9章 9-1）。

### 7-4. `posterize_soft(5, 0.25)` の下端クランプ

`t ≤ 0.0625` が完全な 0（＝100%インク）に落ちる。現行黒点では `face ≤ 0.3794` が該当。
偽ベタ黒への寄与は **−8%**（この段だけ外した差）。帯化としては効いていない（第3章）。

### 7-5. 白点 0.874 が肌の陰の上にある

肌の陰は `face` 0.74〜0.85 で、自動で決まった白点 0.874 の下に入る。
margin（白点 = 最頻値 − margin×幅）を振ると:

| margin | 0.11（s8） | **0.15（採用）** | 0.20 | 0.25 |
|---|---:|---:|---:|---:|
| 腕にトーンが乗る割合 | 9.7% | 8.2% | 6.8% | 5.6% |
| 全体インク絶対誤差 | 0.0634 | **0.0619** | 0.0625 | 0.0651 |

**margin は弱いレバー。** 0.25 まで振っても 5.6% 残り、誤差は 0.15 を超えると悪化に転じる。
7-2 の方が効く。

### 7-6. `compose_alpha(out = dots*(1−line))` が中途半端な線の応答をグレーで出す

服のグレーは網点だけなら 0.79%、最終 2.24%（+1.45pt）。
該当画素の `line` は中央値 0.306（p25=0.14 / p75=0.61）で、
線とも面とも言えない black-hat 応答がそのまま連続グレーとして残る。

### 7-7. `closing(k=7)` が髪の光沢クサビを1段で消す

クサビと周囲の輝度差:

| 段 | 差 |
|---|---:|
| 原画 `g` | 0.1137 |
| `closing(g, 7)` | **0.0028（97.5%消失）** |
| `face` | −0.0001 |
| `t_post` | −0.0008 |

**`box`（`tone_r`）は追加の損失をほぼ生まない。犯人は closing。**
クサビの縁を作る房の筋は幅 p50=2.0px / p90=4.0px で、`close_k=7` は設計どおり全部埋める。

| close_k | 3 | 5 | 7 | 9 | 11 |
|---|---:|---:|---:|---:|---:|
| クサビ差 | 0.0199 | 0.0028 | 0.0028 | 0.0030 | 0.0047 |
| 線とみなす画素 | 1.76% | 2.58% | 2.95% | 3.29% | 3.51% |

**`close_k=3` でも原画の差の17%しか戻らない。** closing を緩める方向では解けない。

### 7-8. `white_line` の `dark_below=0.35` が中間調で不活性

`box(g,5) < 0.35` を要求するが、髪は 0.55〜0.67。クサビの **1.5%** しか拾えていない。
ベタ黒の内部を白く抜くために調整した定数が、髪の輝度帯では効かない。

### 7-9. 出力が2値になっていない

| 出力値 | 割合 |
|---|---:|
| 0.0〜0.1 | 6.52% |
| 0.9〜1.0 | 87.59% |
| 中間グレー（0.05〜0.95） | **6.58%**（後ろ髪 19.76% / 服 2.24%） |

グレー画素の **99.3% は純黒／純白から1〜2px 以内**＝網点の縁である。
ただし**セル 20px² が小さすぎてドットの周長が面積を支配し、
隣接ドットの AA の縁が繋がって連続したグレーの網になっている**
（グレーの最大連結塊 6,410px。上位4塊は `line` 中央値 0.000 / `dots` 中央値 0.50〜0.60）。

一様 0.5 の灰色を網点化したときの中間グレー率:

| ピッチ | 4.47px | 6.71px | 8.94px | 13.42px |
|---|---:|---:|---:|---:|
| 中間グレー | **60.0%** | 26.7% | 30.0% | 20.0% |

中間グレー率だけを見れば細かいほど悪い。**ただしこの掃引は 4.47px より粗い側しか無く、
ここから「細かくすると悪化する」を外挿したのは誤りだった**（8-2 で撤回）。
服のグレーだけは 7-6 由来で、これとは別。

### 原因ではないと確認したもの（同じ調査を繰り返さない）

- **黒点・白点を `face` から測る案（旧 7-1）は誤り。** `t = clip((g − black)/(white − black))`
  は t=1 が白なので、**黒点を上げると暗くなる**。現行（黒点 0.3464）で face=0.50 → t=0.291、
  face 案（黒点 0.5045）では t=0.000＝真っ黒。**旧 7-1 が非難した現象を、旧 7-1 の修正案が起こす。**
  等倍で見ると `g` / `face` とも実用不可だが、**比べると `g` の方が明確にマシ**で、
  face は4症状のうち3つを悪化させ良くなった点はゼロ
  （後ろ髪の `t==0` 割合 g版 0.00% / face版 16.00%、偽ベタ黒 8.77%→15.68%）。
  旧 7-1 の「髪の面輝度は 0.50〜0.66」も誤り（実測は後ろ髪 `face` p2=0.352 / p10=0.392 / 中央値 0.768）。
  「`g` の下位2%は74.6%が線」だけは実測 72.6% でほぼ正しい
- **ベタ黒／`solid` チャンネルは `s8_final` に存在しない。** `line_final` の `solid` 引数は
  s8 から呼ばれていない。構造上、原因から除外される
- **closing は暗くしない。** `min(closing(g) − g) = 0.000000`（濃淡クロージングは恒等以上）で、
  後ろ髪では平均 +0.034 明るくする。「毛の隙間を暗い側で埋めて塊にする」は不成立
- **合成段は黒潰れの原因ではない**（白線 OFF で ±0、線 OFF で −6%）。7-6 のグレーとは別
- **カーブ以降に単調性を壊す段は無い。** `face` を 0.05 刻みで束ねた `face`→最終インク率は
  全画面で単調（破れは 0.30-0.35 帯の1つだけで、posterize の下端クランプ由来。外すと破れ 0）。
  **壊れているのは「`face` がその画素を代表していない」事**（＝7-2）
- **`post_w=0.25` は中間グレーの原因ではない**（第3章）

## 8. 網点ピッチ

### 8-1. 採用は (4,2) = 4.472px / 26.6度。現行アプリは 2.121px

**現行アプリのピッチは 2.121px。** `dotSize` は4プリセットとも 1.5、`scale = PI/1.5`、角度45度、
セル 4.5px²、1160×1536 なら長辺 724行。`tex` が絶対画素座標なので
**画像サイズに依存しない固定値**（作り直し案は長辺追従。2-2）。

**採用は (4,2) = 4.472px / 26.6度。** ピッチ 3.6〜4.5px の整数格子のうち、
45度は縮小で唸り、(3,2) は黒が沈まず、**(4,1) は 14.0度で0度に近く「網戸」側のリスクがあり未検証**。
**残るのは (4,2) だけ**という消去法での採用。

**受け入れる欠点は2つ:**

- **等倍で 26.6度の斜め筋が出る**（網点が斜めの鎖に繋がり、髪の房の流れと干渉する）
- **濃い面が (3,3) ほど黒く沈まない**（髪の真黒率 74.5 対 86.1）

#### (3,3) 4.243px / 45度は撤回した ── 縮小で面が斑になる

一度は目視で (3,3) を採ったが（等倍では斜め筋が出ず、濃い面が黒く沈む）、**撤回する。**

- **縮小率 ×0.67 付近と ×0.83 付近で、面に大きな明暗の斑が出る**
  （41px窓で均した後の誤差が最大26階調）。前髪のトーン面で上部が帯状に白く抜ける。
  **モアレ（縞）ではなく斑**
- **原因は45度そのもの。** 45度は `a==b` でしか作れず x/y の周期が完全に一致するため
  （(3,3) はどちらも 6px）、整数比の倍率で両軸が同時に共振する。
  ピッチ 3.6〜4.5px の候補6種のうち**45度の2つだけが飛び抜けて悪い**（(3,3) 21.0 / (4,4) 38.0。
  45度以外は最悪 3.7）。**45度を選ぶ限り逃げられない**
- **面が斑になるのは斜め筋より重い。** 斜め筋は質感の問題、斑は濃度の誤り
- ×0.50 / 0.43 / 0.33 / 0.25 / 0.13 は3変種とも問題なし
- 補足: **現行アプリ（2.121px / 45度）も同じ ×0.66・×0.83 で唸り、
  中央値ではむしろ現行の方が悪い**（7.5 対 3.4）。山の高さだけは (3,3) が上（21.0 対 14.2）

**2-2 の「`(a,a)` や `(a,0)` は特定の倍率で強く唸る」という既存の記述は正しかった。**

なお (3,3) の等倍での癖として記録していた「中間濃度の広い面が約3px角の市松に見える」
（`t1_darkbg` の黒ボディスーツで目立つ）も、45度で菱形が接するためで、
**幾何からの推測。印刷物との照合は未検証。**

#### (3,2) 3.606px / 33.7度も不可 ── 濃い面で黒が沈まない

3項目は合格した。**斜めの鎖は出ない**（33.7度で鎖が出るという推測は外れた）。
**縮小は全倍率で平坦**（最悪 2.80、×0.67=2.07、×0.83=2.46）。
**ベタ黒保持も退行なし**（t2 83.9 / t4 98.8 / t3 20.1 / t6 52.2 で3案とも同値）。

**不可の理由は1点。セルが 13px² しかなく、どの濃さでも画素の 61.5% が
アンチエイリアスの中間値になる**（T=0.80 では真黒画素がゼロ）。
インク率は正しいので**濃度ではなく質感の誤り**で、面が網点ではなく**平らな灰色の塗り**に見える。
7枚中5枚で濃い面の真黒率が3案の最低（`src_full` 65.67 / t3 60.71 / t5 51.25 / t6 65.39 に対し
(4,2) は 74.5 / 82.7 / 67.7 / 84.7）。面グレー% は6枚でほぼ倍。

#### 縮小の測り方 ── 2-2 の縮小耐性の指標は使えない

- **2-2 の縮小耐性の値（8.72 / 0.01）は、元の実装が `poc/tone/` に残っておらず定義を復元できなかった。**
  趣旨から再構成すると (3,3) が劣る**向き**は再現するが (4,4) の順位が食い違い、同一の指標ではない。
  **この形の指標は箱窓と格子周期の噛み合わせが交絡していて、見え方の判断には使えない**
  （モアレを箱窓で測ろうとしたときも同じ罠に掛かっている。絵柄の無い一様濃度でも同じ差が出た）
- 取り直した基準は「**網点前の連続階調を同じ倍率で面積平均したもの**」との差。0.30〜1.00 を 0.01 刻みで掃引
- **アプリの縮小方法（実測）**: `js/core/settings.js:13` は `imageSmoothingEnabled: true` のみで
  `imageSmoothingQuality` は未設定＝既定 `'low'`。Chrome で実測すると
  **`drawImage` は面積平均（ミップマップ）で縮小しており、素朴な4点バイリニアではない**
- **未確認**: `js/core/settings.js:11` の `renderer: "webgl"` が Fabric のオブジェクト描画まで
  WebGL にするなら結論が変わり得る（`js/ui/third/` は読み込み対象外で未確認）。
  **ただし (4,2) はバイリニア経路でも平坦（最悪 3.74）なので、今回の判断はこの未確認に依存しない**

### 8-2. 「細かくすると悪化する」は誤りだった（撤回）── ただし現行の粒度には届かない

以前ここに「ピッチを細かくするとドットが解像せず灰色のぼけになる」と書いていたが、
**掃引が現案と同じか粗い側だけで、細かい側を1つも試さずに外挿していた**（第0章）。

**細かい側の下限は当初「3.6px」と書いたが、これは1段ゆるかった。**
2.24 / 2.83 / 3.16px は目視で全滅（1px の市松になるか、平坦なグレーになる）で、
**3.606px も既に範囲の外側**（黒が沈まない。8-1）。**現行アプリの粒度 2.121px には到達できない。**

**現行の粒が細かく見えるのは、濃度が原画の 1/3 しか出ていないから**（髪で現行 0.24 対 新案 0.70）。
地が白いので 1px の点が点として見えているだけで、
**正しい濃さを細かい格子に入れると黒画素が一続きの網に融合する**
（淡いトーン面の黒塊サイズは 現行 26px に対し 2.83px 案で 804px）。
**「現行と同じ粒の細かさ」と「正しい濃さ」は両立しない。**
以前「両立する」と書いたのは**濃度応答の話**（誤差23分の1）で、
**点として見えるかとは別問題**だった。

事実記述として残す分: 4.472px は B5判なら約34線相当で、印刷の漫画で普通の 55〜65線より粗い。
ただし 55〜65線はピッチ 2.34〜2.76px＝セル 5〜8px² に当たり、上の理由で成立しない。
印刷で60線が成立するのは 600dpi＝セル 100px² だから。
なお光沢クサビの消失はピッチでは直らない（`face` の段で既に差 0.000。
13.42px まで粗くしても残存差 −0.0118）。

**絵の細部の太さ**（距離変換の稜線、幅 = 2×距離）。ピッチは房の筋より太く光沢クサビと同寸で、
**点1つが絵の細部と同じ大きさになっている**。

### 9-1. 線の暗さゲート（7-3 の手当て）は採らない

`line_darkness(g, 0.36, 0.54) = 1 − smoothstep(0.36, 0.54, g)` は **`g ≥ 0.54` で恒等的に 0**。
白いワンピースの線（`g` p50=0.563）を丸ごと落とし、服の線画残存が 59.3%→**22.4%** になる。
ゲートを外すと 59.2% に戻り、他4件（黒点・`tone_r`・ベタ床・`margin`）はいずれも ±0.5pt で無関係だった。

**絶対輝度では原理的に分離できない。** 残したい服の線（p10=0.148 / p50=0.563 / p90=0.735）が、
止めたい明るい髪の上の線（p10=0.458 / p50=0.497 / p90=0.553）を**完全に内包**している。
切れる閾値が存在せず、**ゲートを絶対輝度で設計した事自体が誤り**だった。
局所コントラストで切る代案も、BH 0.26 で服線 −33.7pt に対し毛先 −5.2pt という
単調に悪いトレードで全滅した。
ゲート無しでも黒点と `tone_r` だけで毛先は s8 比25%改善しており（29.39%→21.96%）、
ゲートが稼ぐのは 3.56pt にすぎない。

**`margin=0.18` は振りすぎ**（全体 out 平均 0.9120→0.9420、後ろ髪の面 cov 中央値 0.250→0.046）。
**0.15** なら 0.9302 で、服の線は変わらない。

  s10 は白のまま

### 9-4. 未検証の課題

s8 / s10 に共通で残る（今回の変更とは無関係）:

- 平坦な中間グレーの背景と、淡いグレーの布のシワが、両案とも白に飛ぶ

- `t6` の左目が髪の黒に飲まれて消える

手当ての当てが無いもの:

- **光沢クサビの復元。** closing が原理的に消すので `close_k` では戻らない（`close_k=3` でも17%）。
  **面のコントラストとして再注入する別経路**が要ると考えられるが、**設計も計測もしていない（推測）**
- **`white_line` の `dark_below`。** 0.35 を髪の輝度帯（0.55〜0.67）まで上げれば拾える可能性はあるが、
  ベタ黒の内部を白く抜く副作用（第2章 2-5 で t3 が 3.1% 抜けた件）が再発する見込み。**未検証**
- **服の中間グレー。** `compose_hard`（`line ≥ hard` を真っ黒に落とす）で中途半端な `line` が
  消える可能性はあるが、線の AA が失われる見込みで**未計測**
- **`ss` を 2→1。** 一様0.5の濃度誤差は ss=1/2/3 のいずれも 0.0000 なので処理量を 1/4 にできる
  余地があるが、**ドット形状の劣化を評価していない**
- **黒点 固定0.10 の外れ方。** 7枚で破綻しなかっただけで、**紙が灰色に転んだスキャン原稿など、
  地の黒点が 0.10 より上にある入力は試していない。** 地が黒く沈むはずだが未検証
- **黒点を下げると髪のインク率が原画より 0.03〜0.06 薄くなる**（`src_full`）。
  gamma / knee で戻すべきかは未検証

### 9-5. 線の濃さは `line_gain` では振れない ── `line_thr` に替えた

`compose_full` は `out = dots*(1−line)` の乗算合成なので、
**`line_gain < 1.0` だと線の出力値が `255*(1−gain)` より下がらない。**
実測で 薄い（gain 0.85）の線の最暗値 38.3、シンプル（gain 0.70）で **76.5＝中間グレー**。
**両者とも線として黒（≤32）になった画素が 0%。**
さらに `line_gain` は `np.maximum` で足したベタ床にも掛かるため、
ベタ黒の出力平均が 薄い 13.2 / シンプル 13.8 と黒くならない。
目視で「シンプルがかすれ・退色に見える」原因はここ。

**`line_gain` を捨て、`line_thr`（black-hat 閾値の倍率＝拾う量＝太さ）に替えた。
ベタ床は線の加工のあとに足す順序に変更した。**
修正後は4プリセットとも出力最小 0.0、ベタ床の出力平均 0.54 に揃う。
閾値を下げすぎると面に偽の線が立つので下限は `BH0*k >= 0.038`（面の応答 p99）から k=0.70。

**採らなかった案（線アルファに冪）:** 黒には届くが可動域が線画素率で 1.12倍しかなく、
「濃さ」の軸が残るので線の裾が中間グレーのまま。採った案の可動域は 1.53倍。

**「線の太さは `line_thr` で振る（`line_gain` は濃さだけで太さは変わらない）」は正しかった。**

### 9-6. 4プリセット対応 `s11` ── 条件付きで採用可（条件の1つが未検証）

**`s10` は変更せず、`s11` を新設した**（`lead_stages.py` の `S11_PRESETS`）。
`s11(gamma=1.0, levels=5, post_w=0.25, tone_r=2)` は `s10(rgb)` と**画素単位で完全一致**（最大差 0.0）。

- **黒点固定 0.10 のもとでは、濃さの可動域が現行より狭い。**
  現行は「網点が乗り始める輝度」自体を動かして濃さを作っていた（1-5）が、
  `s10` は開始点を自動白点に固定したため gamma は密度だけを変える。開始点を動かすと紙の判定が壊れる
- **濃さ（gamma）だけで4つを作ると見分けられない**（目視で確認）。
  現行は濃さでなく**質感**が違っていた（薄い＝均一網点 / ラフ＝疎な点＋細線 / シンプル＝ベタ黒）
- **`knee_hi` は捨てた。** 可動域は広いが `t/hi` のクリップは実質的に白点を下げるのと同値で、
  掃引した全点で「明部構造の保存率」が落第。
  **ただしこの指標は後に信用できないと判明している（第10章）ので、この落第は根拠として弱い。**
  白点を下げるのと同値である事自体は残る
- **2-4 の「白点を動かすと紙の判定がずれる」は、黒点を固定しても成り立つ**（実測で確認）
- `tone_r` は濃さの軸として捨てた（面が動かず光沢クサビだけ平らになる）

#### 目視判定の結果 ── 4つは見分けられる

**通ったもの:**

- **4つを見分けられる**（髪で判定）。薄い＝疎な規則格子 / 濃い＝密な規則格子（薄いとの差は約2倍） /
  ラフ＝まだら・かすれ状のテクスチャ / シンプル＝ベタ黒＋白帯
- **現行との差は十分に大きい。** 現行はピッチが細かすぎて等倍では網点に見えず、
  平坦なグレーとして読める（8-2）。**4段の差も現行より明確に大きい**
- **線が黒く出ない不具合は解消**（4プリセットとも太く真っ黒で連続。9-5）。
  現行は線が端に向かって薄いグレーに消えて途切れる
- **光沢クサビは4プリセットとも白い筋として残った。** 現行はラフでコントラストがほぼ無く、
  `s11` の方が良い
- **肌に網点が乗る事自体は問題ではない。** 濃い・ラフでは腕の影の形に乗り、陰影として読める

**識別性の弱点（記録）:**

- **服の列は4つともほぼ同一**（白＋線のみ）。元画が白いワンピースで中間調が無いためで、
  **題材の問題であって処理の問題ではない**
- **腕の列では薄いとシンプルがどちらも白一色で区別できない**
- 差が出るのは**中間〜暗部のトーン領域だけ。プレビューに服だけを出すと違いが見えない**

#### 目視判定で挙がった3件の手当て ── すべて意図どおり直った

**1. ラフの外形線が点列に分解する。**
`line_rough` を 0.55→0.25 に下げて一度直したはずの「線の点線化」と同じ見え方で、
0.25 でもまだ壊れていた。**`line_rough` は4プリセットとも 0.0 にし、ラフさは
`tone_noise` 0.35→0.45 のみで出す。** 外形線は連続した黒線に戻った。

- **外形線と内部線の分離は試みたができなかった。**
  black-hat の深さで閾値 0.40 を引いても外形の 28.6% が内部側に落ちる。
  線は1画素抜ければ破線に見えるので、71% の保護では足りない
- **「かすれ」は実は効いていなかった。** 旧実装が効いて見えたのは芯を削って線を切っていたからで、
  芯を残す形にすると `line_rough=2.00` でも平均絶対差 0.80/255 しか動かない
- 識別性は `tone_noise` だけでも成立し、濃いとの差は 14.6→**15.3** に広がった。
  線残存 85.59→**87.33%**、服線残存 70.82→**73.06%**

**2. 薄いの腕に出るまばらな点の小片。** 原因は `levels=3` の量子化の上側斜面で、
腕領域の 4.65% が t∈[0.95,1.0)（網点面積率 3〜5%）だった。
**`tone_snap=0.93` を新設（薄いのみ）して落とす方を採った。**
元の点も上端が元絵に対応しない人工的な水平の境界で切れており、**「影」ではなく「汚れ」だった。
現行アプリも腕は白なので、失ったものは無い。**

**3. シンプルが中間の暗さの面を潰す。** `solid`（絶対 0.35）を
**`solid_rel=0.333`（床の閾値を自動白点で正規化）に替えた。**
`t1_darkbg` 18.47→**15.73%**、`t5_solidblack` 10.57→**5.86%**。`src_full` では絶対 0.35 と完全に同値。

- **ベタ黒の白飛びは無い。** t5 でベタ黒率が半減した箇所は元絵が銀髪（中間の灰色）で、
  そもそもベタ黒にすべきでない領域だった
- **ただし潰れは半分しか直らない。** 「黒い塊のまま」ではなく**「半分は塊のまま」が正確**で、
  `t1_darkbg` の衣装は下半分が50%トーンになり縫い目線とハイライトの弧が読めるが、
  残る左上側の約半分はベタ黒で、黒とトーンの境界が**元絵に無い硬い斜めの線**として立つ
- **`solid_rel=0.24` は t1 の衣装を最も良く描くが、同じ値で `src_full` の髪のベタ黒が
  丸ごと50%トーンに崩れ、シンプルが濃いと区別できなくなる。0.333 は髪のベタ黒を保つ限界点**

#### 採用の条件3つ

1. **シンプルに適用範囲の注意書きが要る。** 中間の暗さの大面積（濃色の衣装など）では
   形の半分がベタ黒の塊になる。**そうした絵では「濃い」の方が良く出る**（同じ衣装を階調付きで描き切る）
2. **`tone_snap` をなだらかな階調の絵（`t3_softshade` 相当）で検証する必要がある。未検証。**
   現状のサンプルでは検証不能（大面積のなだらかな階調が腕しかなく、
   その腕は全域が白に落ちるので段が生じる状況自体が起きない）。**ここだけが残ったリスク**
3. 下の別課題2件を記録した上で採ること

#### 別課題（今回の修正とは無関係。現行アプリにも存在する）

- **線周りに残る連続階調の灰色。** 網点でも黒でもない筆跡が残り、
  二値＋網点であるべき出力に中間調が混じる。**見方が2つあり、どちらも記録しておく。**
  実装側の測定では「服領域の中間グレー 1.52〜1.97% のうち 98〜99% は線の縁2px以内の AA で、
  面としてのグレーは 0.01〜0.06%。正体は `smoothstep(BH0,BH1,·)` のランプそのもので、
  硬くすると線がジャギーになるので手当てしていない」。
  判定側は同じ箇所を**目に見える筆跡**として捉えている。
  なお脇の縫い目に AA ではない黒い滲みの塊が1箇所あり、**これは未対応**
- **淡いグレーの服の陰影が全プリセットで消える。** ワンピースの襞の影を4プリセットとも完全に落とし、
  服が輪郭線だけの白い面になる

#### 未解決として残っているもの

- **シンプルの潰れは半分残る**（上記 `solid_rel=0.333` の限界点）
- **`薄いカラー化`（`c2c.js`）は未対応・未再現。** 検証台に alpha 0.4 のカラー重ねも
  webp 再エンコードも無い
- **アプリのコード（`js/`）は1行も変えていない**（9-3）

## 10. 指標セット ── 目視の答えで検定する

**現行の指標は、目視で挙がった11観点のうち3つしか測れていなかった。**
とくに **s8 の最大の失点である「光沢クサビの消失」を1つも捉えていない**（第0章）。

`poc/tone/metrics.py` に7指標を足し、**既に出ている目視の答えを正解ラベルとして検定した**
（10ラベル中8つを再現）。すべて原画基準の相対量で、部位ごとに測る。
のちに「点分離px」を8つ目として足した（原画基準ではなく一様パッチで測る）。

| 指標 | 何を見るか | 効いた例 |
|---|---|---|
| ~~明部構造の保存率~~ | 原画でクサビが周囲より明るかった量が、出力に何割残ったか。**信用できない（下記）** | s8 **−1.362** / face −1.143 / s9 0.587 / s10 0.450 |
| 点分離px | 一様面での黒塊と白隙間の連結塊サイズ（4連結・中央値、t=0.4〜0.8 の最小）。網点が点として出ているか | 2.24px→0.0 / 2.83→0.0 / 3.16→0.0 / 3.61以上→4.0 |
| 線連結 | 原画の線画素のうち10px以上つながった黒になった割合。消失と点線化を1つで測る | 服レース s9 **21.95** / s8 55.99 / s10 56.02 |
| 線太さ比 | 線が太る／細る | face 2.460 / s8 1.925 / s10 1.565 |
| 濃度比（部位別） | 面が濃すぎ／薄すぎ | s9 髪 0.887・後ろ髪 0.772（薄い）/ face 1.563（濃い） |
| 真黒率 / 近傍汚染 / 面グレー% | 面グレーは純黒・純白から2px超離れたグレーだけを数え、AA の縁と区別する | s10 の真黒率低下を検出（9-2） |

**「明部増」は破棄した。** 4案すべて −0.10〜−0.11 で区別が付かず、ラベルを再現できない。
**再現できない指標は捨てる。**
不可と分かっている face 案が全指標で最下位になり、落とすべき案を落とす対照として機能した。

**「明部構造の保存率」（光沢クサビ）も信用できないと判明した。**
分母（原画のクサビと周囲の中央値の差）が **0.0088 = 2.2/255** しかなく、出力側の差も1〜3階調。
中央値が 3/255 動けば符号が反転し、実際 `levels=3` で +0.84、`levels=4` で −0.95 と隣の段数で飛ぶ。
**この指標での合格・落第は根拠にならない。**
上の表の値と、この指標を根拠にした判断（9-6 の `knee_hi` 却下など）はすべてその前提で読む。

**画素値の分布では 1px 市松と網点を区別できない。**
一様 t=0.5 の内訳は (2,2) が真黒 27.8% / 純白 27.8%、(4,2) が 35.6% / 31.1% で、
**(2,2) の方が統計的には「2値らしい」のに、空間スケールが 1px なので面に見える。**
上の「点分離px」はこれを埋めるために足した指標で、既知の目視の答えを再現している。
**4連結にするのは、1px 市松が8連結だと全部つながって区別できなくなるため。**
合格ライン 2.0 は暫定で、**3.61px を合格にする点で境界がやや甘い**。

### 測れないもの

- **症状4（トーンが荒い）** ── 当初は4案とも網点ピッチが同じ定数で比較軸にならなかった。
  ピッチを振った掃引（8-1 / 8-2）と「点分離px」で部分的に測れるようになったが、
  **粗さそのものの合否は目視でしか出ていない**
- **症状3（肌に網点）** ── **原画基準の相対量では原理的に測れない。**

  **原画に無い様式の要求**だから。代用できるのは出力の絶対量だけで、絵柄に左右される

- 色で切った部位マスクは線の画素を含まないため、服・肌の線指標が 0.00 になる。**線は矩形領域で測る**
